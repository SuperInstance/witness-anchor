What the fleet got wrong

The fleet spent a year calling its logs "tamper-evident" when they were not. A careful sweep of six repos produced 47 corrections, and the finding that no log in the fleet holds all three legs:

legwhat it meanswho holds it
1 · re-derivesthe chain recomputes from its own bodieseverybody
2 · signedthe head carries a signature from a key we trusttwo ledgers, optionally
3 · published out of bandthe head is published where the log writer does not control itnobody
A Worker on the fleet's own Cloudflare account is not out of band. The log writer can push to the account. So a self-anchored chain is attested — whatever the publisher asks for.

The classification, and the refusal

same account                -> attested    "self-anchored: the log writer can re-publish it"
different account,
  ASSERTED by publisher      -> attested    "ASSERTED, not OBSERVED — no security
                                          property can rest on it"
different account,
  OBSERVED by the anchor     -> tamper-evident

publisher claims more       -> REFUSED, and the refusal is stored
row-checksum log            -> not a chain: nothing to re-derive FROM

And it is the account, not the storage

R2 and KV are both writable by the account, so neither is out of band by itself. What the anchor can do is make a rewrite visible: the first head for a chain is the anchor, every later publication is an epoch, and the divergence is recorded.

The workaround: Vectorize is remote-only

Binding VECTORS needs to be run remotely

That is what a local Worker gets when it touches a Vectorize binding. So the fleet's Vectorize code — prism's 18 KB worker, the papers' indexing scripts — cannot be executed by anyone without an account. Two backends, one interface:

backendwhensearch
vectorize-annthe binding is presentapproximate (ANN)
d1-exactotherwiseexact — brute-force cosine over D1

The Worker cannot tell them apart, and every response says which one served it, so an approximate answer is never passed off as an exact one. The exact backend is not a toy: its answer is the truth, and the ANN path is the approximation it should be checked against.

Three things fall out, and they are the design

  • On the literal question the judge is not merely better — it is perfect on precision (10/10, no false positives) while the index makes 7 false positives in 10. An index cannot decide. It can only propose.
  • On the intent question the two are equal — and the index is free, offline and deterministic. So the index is not a cheaper judge; it is a different instrument that is equally good at the harder question.
  • The union is bigger than either, because they find different positives. Index proposes, judge decides.

A rule, observed: a gateway failure is never converted into a score. One document failed; it was excluded from the denominator and reported, not scored 0. Scoring a transport error as "no" would inflate recall by turning every failure into a correct negative.

Three bugs the local test caught

Running it for real, with no account, found three things that would have shipped:

1 import { createHash } from 'node:crypto' — a Worker cannot import a Node builtin without nodejs_compat, and workerd will not resolve it. Replaced with WebCrypto, so the canonicaliser now has no deployment constraint at all.

2 Buffer.from(s,'utf8') — Buffer is a Node global and does not exist in a Worker. This would have been a runtime error on the first calculator-quilt chain, in production, with no warning.

3 A multi-line D1 statement (miniflare's exec() fails on one) and values being a SQLite reserved word.

The one build that would change the fleet's vocabulary

Run the anchor on a second Cloudflare account, and have the log writer publish to it. Then the anchor can observe that the log came from the first account, rather than being told — and the class becomes tamper-evident for real.

That is one build, not a redesign. And it is the only thing in the fleet that would make "tamper-evident" true.
